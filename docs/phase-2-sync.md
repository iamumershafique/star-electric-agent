# Phase 2: sync safety (in progress)

## What the warning banner means

- An individual PR/DC write is **pending** until Firestore acknowledges it. While offline, the promise can stay pending; keep the tab open and verify the record on another authorized device after reconnection.
- **Failed** means that operation was rejected. It is not retried by the warning system. Confirm the actual record and contact the administrator before acknowledging the warning.
- After a reload, previously pending operations become **unconfirmed**, not successful. Warnings use session storage, may not survive closing the tab, and are not a durable retry queue. If session storage fails, the banner says warnings cannot be persisted.
- A stopped live subscription is reported until the listener receives a server-backed snapshot again. A cached snapshot does not clear the warning. Reloading or signing in again may reconnect it; verify the actual data afterwards.
- If local ledger storage fails, the existing local cache and pending image keys are preserved, and a warning is shown for that page lifetime. Do not close the tab or clear browser data until the data has been preserved. The warning itself may not survive reload.
- A browser offline indication is advisory; being online does not prove Firebase is reachable or that records are synchronized.
- Snapshot comparison appends cloud-only records by ID and warns about conflicting values, duplicate IDs/numbers, or local records absent from an authoritative server snapshot. During a live subscription, a later authoritative server update can refresh a local record only when its non-image fields still match the preceding authoritative server snapshot and its ID and number are unambiguous. The first snapshot cannot prove a local cache is unchanged. Cached, pending, or incomplete snapshots never authorize an update; invalid documents discard the baseline. Local image fields are retained rather than reconciled.
- Absence could mean deletion or a record never uploaded; nothing is automatically deleted. Differing local edits are preserved. PR/DC edit forms also check their original data, including image references, against the current local record before saving, so an open stale form cannot silently replace a refresh. This is a local check only, not a Firestore transaction. Known discrepancies block this app's ordinary PR/DC cloud writes, but local edits can already have been made and must be preserved. The warning is not a reconciliation tool.
- A rejected or pending scan upload is now reported in the same warning banner; a local IndexedDB scan-save failure is also reported. These warnings only cover attempts made while the app is listening, and do not establish that all historical scans are present. Snapshot cache updates do not re-upload hydrated scans.

The bulk **Push All Data** operation is disabled because it could overwrite newer cloud records with stale local copies and previously reported success despite failures. Do not work around this guard by calling older deployments or scripts.

## Not yet fixed

These warnings cover attempted PR/DC cloud saves, deletes, scan uploads and listener errors. They do **not** prove that all records or scans are synced. Snapshot comparison does not compare scan contents and may report harmless differences in legacy fields. It cannot refresh a locally different record or provide a conflict-resolution interface. The baseline exists only while the subscription is active and does not prove the source data is correct. The known-conflict and open-form guards are not server-side transactions: another device can change data between the last snapshot and a write, and other legacy code paths can bypass the guards. Some existing link and builty paths modify only local records. Scan object keys can still collide, historical scans may be missing, and upload attempts do not form a durable queue. Cross-device transactions, atomic PR/DC updates, deletion reconciliation, and reliable offline retries remain unfinished. Acknowledging a warning does not save, retry, or reconcile anything. Don't deploy as production-ready until these issues and the Phase 1 backup/restore checklist are addressed.

Application tests use simulated Firebase services and storage failures. Security-rule tests run against Firebase emulators with synthetic records, not a live Firebase project. No production data was accessed as part of this work. Firebase Storage download URLs and external scan links have separate confidentiality limitations; see [role migration](./role-migration.md).
