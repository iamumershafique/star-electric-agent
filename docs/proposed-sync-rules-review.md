# Experimental local sync rules — not deployment-ready

`rules-tests/proposed-sync.rules` is a separate test-only design. It does **not** replace `firestore.rules`, is not referenced by `firebase.json`, and must not be published. The corresponding experimental backend is `src/lib/demoSync/proposedBackend.ts`, fixed to a demo project and loopback. It does not authenticate a real portal user; it is connected to the Quick Dispatch handler only behind the isolated demo switch, not to production sync.

## Intended protocol

A receipt under `star_sync_actors/{actor}/operations/{operation}` records the authenticated actor, operation ID, PR/DC IDs, expected prior revisions and a payload fingerprint. Each written record carries `_sync` with the same actor and operation and its incremented revision. The proposed rules require a new matching receipt and corresponding after-state(s) in the same atomic write, deny changes to receipts, require a matching PR for linked DCs, and prohibit changes to existing top-level scan fields. Creates use revision 1; existing unversioned records are not automatically adopted. The demo worker reads the receipt first, so retrying an identical command after an acknowledgement loss returns duplicate rather than applying it again.

This is a design to be tested, **not a proven authorization boundary**. Official-emulator tests exist in `rules-tests/proposed-sync-security.mjs`, but could not run here. They cover roles, direct writes, receipt forgery/alteration, partial linked writes, legacy records, and scan references. `npm run test:rules:proposed` starts the official demo Firestore and Storage emulators, uses loopback guards, and runs those tests. The prior `npm run test:rules` continues testing the existing repository rules.

## Known gaps requiring review before any integration

- Rules cannot verify that the supplied SHA-256 fingerprint corresponds to the record payload. The transaction client calculates it but a malicious authenticated editor can choose another value. The current design binds the receipt to actor, operation, target IDs and revisions, but does not enforce business quantities or full payload integrity. Review the threat model and whether trusted server code or a different protocol is required.
- Top-level scan protection does not verify scan access, and does not enforce preservation of nested scan references in fulfillment arrays. The prototype refuses scan-bearing records; it does not implement real scan reconciliation, upload or safe merging.
- PR item or fulfillment-log edits require a DC in the proposed rules; standalone edits to PR items therefore need a different carefully reviewed policy. Admin deletes are still allowed directly and can leave broken links. Batch actions and legacy maintenance/Drive paths remain unintegrated.
- The `DemoOutbox` can retain a synthetic legacy/scan draft explicitly marked for review, but it is not connected to portal local caches, forms, auth, UI or real scan storage. Its tests use `fake-indexeddb`, not a real profile restart. `prepareDCAndFulfillPR` is a pure preparation step, but its existing persistence wrapper still writes separate local keys.
- Unversioned records must be preserved for explicit review; no migration or inference has been implemented. Server snapshots, conflict review, client/device identity and user isolation need end-to-end work.
- The `hidane` emulator does not enforce Security Rules. Passing its transaction tests says nothing about rules correctness. The official test could not start because the environment blocks downloading the emulator JAR from the Firebase hosting domain. Java 21 was installed only in `/tmp` for the attempt.

## Older open tabs if these rules were ever deployed

These rules are not being deployed. If eventually deployed unchanged, an old tab's ordinary PR/DC create or edit would generally be denied because it does not write the required new operation receipt and revision transition. An existing unversioned record would also be denied. That tab can still save its local cache before the denial; its warning mechanism is not a durable outbox. A pending Firestore write may already have committed before a rules change or may be rejected after reconnecting; this cannot be inferred from the local UI. Administrators' old direct delete calls would still be allowed by this proposal, so deletes remain a separate safety gap. Old tabs would not automatically acquire or migrate queued edits into the new protocol, and users must not clear their storage. Any rollout needs a staged client/rules compatibility plan, explicit old-tab handling, a verified recoverable backup, and separate user approval before production reconciliation.
